Версия 1.1 · 13 ноября 2026

> Документ восстановлен на основе разделов 1–3 исходного ТЗ. Исходный файл обрывался на разделе 3.4, поэтому разделы 4–10 составлены заново и являются продолжением исходного документа. Разделы 1–3 остаются без изменений и имеют приоритет.

## 4. Стек и структура проекта

### 4.1. Базовый стек

| Слой | Технология |
|---|---|
| Язык | Python 3.12 |
| HTTP | FastAPI + Uvicorn |
| Валидация | Pydantic 2 + pydantic-settings |
| ORM | SQLAlchemy 2.0 (async) |
| БД | PostgreSQL 16 |
| Кэш, rate limit, права | Redis 7 |
| Миграции | Alembic |
| Аутентификация | JWT (PyJWT), refresh-токены с ротацией, TOTP (pyotp) |
| Файлы | локальное файловое хранилище с интерфейсом для S3-совместимого провайдера |
| Тесты | pytest + pytest-asyncio + fakeredis + aiosqlite |
| Запуск | Docker Compose |

### 4.2. Архитектура

Модульный монолит. Код разделён на слои:

```text
app/
  core/        конфигурация, БД, Redis, безопасность, ошибки, лимиты, storage
  models/      SQLAlchemy-модели
  schemas/     Pydantic-схемы запросов и ответов
  services/    бизнес-логика (auth, организации, каталог, объявления, поиск, модерация)
  api/         FastAPI-роутеры (публичные, кабинет, /admin)
  seed.py      идемпотентный seed платформенных ролей, тарифов, категорий
```

Правила:

- Роутеры не содержат бизнес-логики: только разбор запроса, вызов сервиса и формирование ответа.
- Проверка прав — всегда по коду разрешения, не по названию роли.
- Публичные и административные API разделены префиксами `/api/v1/*` и `/api/v1/admin/*`.
- Все ошибки возвращаются в едином формате.
- Все операции модерации и администрирования пишутся в audit log.

### 4.3. Конфигурация

Все настройки — через переменные окружения (`.env`). Секреты в репозиторий не попадают. Обязательные в production: `SECRET_KEY`, `DATABASE_URL`, `REDIS_URL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET`.

## 5. Данные

### 5.1. Основные сущности

- `users` — пользователь Telegram/телефон/email, статус, настройки уведомлений.
- `refresh_tokens` — refresh-токены в виде SHA-256 хэша, семейства токенов, признак MFA.
- `login_sessions` — одноразовые сессии входа через Telegram deep-link.
- `platform_roles`, `user_platform_roles` — платформенные роли и их назначение.
- `totp_secrets` — TOTP-секреты платформенных пользователей (шифруются).
- `organizations` — организация, реквизиты, регион, публичный slug, тариф, верификация.
- `org_members`, `org_roles` — сотрудники и кастомные роли организации.
- `invitations` — одноразовые приглашения на 72 часа.
- `capabilities`, `organization_capabilities` — теги возможностей и их JSONB-параметры.
- `verification_documents` — документы на проверку модератором.
- `categories`, `category_attributes` — дерево каталога до 3 уровней и атрибуты.
- `listings` — объявления, JSONB-атрибуты, статус, контакты, срок публикации.
- `listing_promotions` — топ, выделение, поднятие.
- `listing_views`, `favorites` — просмотры и избранное.
- `complaints` — жалобы на объявления, организации и пользователей.
- `plans` — тарифы организации (лимит активных объявлений).
- `audit_logs`, `platform_settings`, `uploaded_files`.

### 5.2. Правила хранения

- Первичные ключи — UUID.
- Время — `timestamptz` в UTC.
- Атрибуты объявлений и параметры возможностей — `jsonb` с GIN-индексами.
- Полнотекстовый поиск — `to_tsvector('russian', title || ' ' || description)` с GIN-индексом.
- Refresh-токены и токены приглашений/входов хранятся только как SHA-256 хэш.
- TOTP-секреты шифруются ключом, производным от `SECRET_KEY`.
- Мягкое удаление объявлений: `deleted_at`; объявления исключаются из публичных выборок.

### 5.3. Индексы под производительность

- `listings(status, published_at desc)`, `listings(category_id, status)`, `listings(region, status)`, `listings(organization_id)`, `listings(price)`.
- GIN по `listings.attributes` и `organizations.capabilities` (через таблицу).
- GIN по полнотекстовому вектору.
- Уникальные индексы: `users.telegram_id`, `users.phone`, `organizations.slug`, `organizations.inn`, `refresh_tokens.token_hash`, `login_sessions.token_hash`, `invitations.token_hash`.

## 6. API

Базовый префикс: `/api/v1`. Формат — JSON. Аутентификация: `Authorization: Bearer <access>`.

### 6.1. Общие правила

- Успешные списки: `{ "items": [], "total": 0, "page": 1, "per_page": 20, "pages": 0 }`.
- Ошибки: `{ "error": { "code": "...", "message": "...", "details": ... } }`.
- Коды: 400, 401, 403, 404, 409, 410, 422, 429, 500.
- Публичные эндпоинты не отдают контакты без авторизации.
- Все даты — ISO 8601 UTC.
- Rate limit: заголовок `Retry-After` при 429.

### 6.2. Auth

| Метод | Путь | Описание |
|---|---|---|
| POST | `/auth/telegram/start` | Создать одноразовую сессию, вернуть токен и `t.me`-ссылку |
| POST | `/auth/telegram/poll` | Опросить сессию; после подтверждения вернуть пару токенов |
| POST | `/auth/refresh` | Ротация refresh-токена |
| POST | `/auth/logout` | Отозвать refresh-токен |
| POST | `/auth/logout-all` | Отозвать все токены пользователя |
| GET | `/auth/me` | Текущий пользователь |
| POST | `/auth/totp/setup` | Создать TOTP-секрет (только платформенные роли) |
| POST | `/auth/totp/enable` | Включить TOTP и получить MFA-токены |
| POST | `/auth/totp/verify` | Подтвердить TOTP и получить MFA-токены |
| GET | `/auth/providers` | Список провайдеров входа |

Access-токен: 15 минут. Refresh: 30 дней, ротация при каждом использовании, повторное использование отозванного токена отзывает всё семейство. Блокировка пользователя отзывает все токены.

### 6.3. Пользователи

| Метод | Путь | Описание |
|---|---|---|
| GET | `/users/me` | Профиль |
| PATCH | `/users/me` | Имя, email, настройки уведомлений |
| GET | `/users/me/favorites` | Избранные объявления |

### 6.4. Организации и роли

| Метод | Путь | Описание |
|---|---|---|
| POST | `/organizations` | Создать организацию (создатель — owner) |
| GET | `/organizations/mine` | Мои организации |
| GET | `/organizations/{id}` | Организация для участника |
| PATCH | `/organizations/{id}` | Профиль и контакты (по разрешениям) |
| PUT | `/organizations/{id}/capabilities` | Возможности организации |
| POST | `/organizations/{id}/verification/inn` | Проверка ИНН по контрольной сумме |
| GET/POST | `/organizations/{id}/verification/documents` | Документы верификации |
| GET | `/organizations/{id}/members` | Сотрудники |
| POST | `/organizations/{id}/invitations` | Приглашение по одноразовой ссылке (72 ч) |
| DELETE | `/organizations/{id}/invitations/{invitation_id}` | Отозвать приглашение |
| POST | `/invitations/{token}/accept` | Принять приглашение |
| PATCH | `/organizations/{id}/members/{user_id}` | Сменить роль сотрудника |
| DELETE | `/organizations/{id}/members/{user_id}` | Удалить сотрудника |
| POST | `/organizations/{id}/transfer-owner` | Передать владение |
| GET/POST | `/organizations/{id}/roles` | Роли организации |
| PATCH/DELETE | `/organizations/{id}/roles/{role_id}` | Изменить/удалить роль |

Owner имеет все разрешения. Кастомную роль нельзя удалить, пока она назначена. Нельзя выдать роли разрешение, которого нет у выдающего (кроме owner). Кэш прав в Redis сбрасывается при изменении роли, состава участников и владельца.

### 6.5. Каталог

| Метод | Путь | Описание |
|---|---|---|
| GET | `/catalog/categories` | Дерево активных категорий |
| GET | `/catalog/categories/{id}` | Категория с унаследованными атрибутами |
| GET | `/catalog/capabilities` | Справочник возможностей |
| GET | `/meta` | Регионы, типы организаций, типы объявлений, разрешения |

### 6.6. Объявления

| Метод | Путь | Описание |
|---|---|---|
| GET | `/listings` | Поиск с фильтрами и сортировкой |
| GET | `/listings/{id}` | Карточка; контакты только после входа |
| GET | `/listings/mine` | Мои объявления |
| POST | `/listings` | Создать черновик |
| PATCH | `/listings/{id}` | Изменить |
| DELETE | `/listings/{id}` | Мягко удалить |
| POST | `/listings/{id}/submit` | Отправить на модерацию |
| POST | `/listings/{id}/archive` | В архив |
| GET | `/listings/{id}/stats` | Статистика просмотров |
| POST/DELETE | `/listings/{id}/favorite` | Избранное |
| POST | `/listings/{id}/complaints` | Жалоба |

Поиск: `q`, `category_id` (с потомками), `type`, `region`, `price_min`, `price_max`, `org_id`, `sort` (`date`, `price_asc`, `price_desc`, `relevance`), `page`, `per_page`, фильтры атрибутов `attr.<key>=...`, `attr.<key>.min`, `attr.<key>.max`.

Публичная выдача — только `active` и не истёкшие. Топ-продвижение влияет на сортировку, выделение отдаётся флагом.

### 6.7. Админ-API

Префикс `/api/v1/admin`. Все методы требуют платформенное разрешение и `mfa=true` в access-токене (Telegram + TOTP).

| Группа | Разрешение | Методы |
|---|---|---|
| Пользователи | `users.view`, `users.block` | список, карточка, блокировка, разблокировка |
| Платформенные роли | `roles.manage_platform` | CRUD, назначение/снятие |
| Организации | `orgs.verify` | список, карточка, решение по верификации, тариф |
| Объявления | `listings.moderate` | очередь, approve/reject/block, продвижение |
| Жалобы | `complaints.handle` | список, решение |
| Каталог | `catalog.manage` | CRUD категорий и атрибутов |
| Тарифы | `plans.manage` | CRUD тарифов |
| Аудит | `audit.view` | журнал действий |
| Настройки | `settings.manage` | чтение/запись |
| Дашборд | любое админ-разрешение | сводные счётчики |

### 6.8. Telegram

`POST /telegram/webhook` — вебхук бота. Проверка заголовка `X-Telegram-Bot-Api-Secret-Token`. Бот обрабатывает `/start login_<token>`, `/start invite_<token>` и получение контакта. Контакт подтверждает телефон без СМС.

## 7. Нефункциональные требования

- p95 поиска < 300 мс на 50 000 активных объявлений при прогретом кэше.
- Публикация объявления — не более 3 минут от регистрации до отправки на модерацию.
- Модерация — SLA 24 часа; очередь сортируется по времени отправки.
- API идемпотентно к повторным poll/refresh в рамках правил токенов.
- Пароли не используются; телефон подтверждается Telegram-контактом.
- Секреты — только в env; логи не содержат токены, телефоны и TOTP-секреты.
- Все изменяющие админ-операции — в audit log.
- Ограничение размера загрузки — 20 МБ; типы файлов проверяются.
- CORS настраивается списком origin.
- Горизонтальное масштабирование API возможно при общем PostgreSQL и Redis.
- Данные и провайдеры — в РФ (требование заказчика).

## 8. Инфраструктура

- Docker Compose: `api`, `postgres`, `redis`.
- Миграции: `alembic upgrade head` при старте контейнера.
- Seed: `python -m app.seed` (идемпотентно).
- Файлы: volume `media/`, раздача через `/media`.
- Health: `GET /health` (процесс), `GET /ready` (БД + Redis).
- Логи: stdout, JSON-совместимый формат в production.
- Резервное копирование PostgreSQL — ежедневно, хранение 14 дней.
- Секреты — через env/secret manager, не в образе.
- Домен API и вебхук Telegram настраиваются через `scripts/set_telegram_webhook.py`.

## 10. Задачи для агентов и критерии приёмки

### 10.1. Каркас

- Приложение стартует, `/health` и `/ready` отвечают.
- Ошибки в едином формате, OpenAPI доступен.
- `alembic upgrade head` создаёт схему; `python -m app.seed` идемпотентен.

### 10.2. Auth

- `start` создаёт сессию и ссылку `t.me/<bot>?start=login_<token>`.
- Бот подтверждает контакт, `poll` один раз выдаёт пару токенов.
- Access 15 минут, refresh 30 дней, ротация; повторное использование отзывает семейство.
- `logout-all` и блокировка отзывают все токены.
- Платформенная роль без TOTP не получает доступ к `/admin`.

### 10.3. Организации и роли

- Создатель — owner; owner имеет все права.
- Шаблоны ролей создаются автоматически.
- Нельзя удалить назначенную роль; нельзя выдать чужие разрешения.
- Приглашение одноразовое, 72 часа, принимается только авторизованным пользователем.
- Изменение роли сбрасывает кэш прав.

### 10.4. Каталог

- Дерево не глубже 3 уровней.
- Дочерняя категория наследует атрибуты.
- Обязательные и типовые атрибуты валидируются; неизвестные ключи отклоняются.
- Категория разрешает только свой поднабор типов объявлений.

### 10.5. Объявления

- Черновик не виден публично.
- Публикация проверяет лимит тарифа/частного лица.
- После approve объявление активно 30 дней; reject требует причину.
- Контакты не отдаются без авторизации.
- Жалоба доступна авторизованному пользователю, кроме владельца объявления.

### 10.6. Админ-API

- Каждый эндпоинт проверяет конкретное разрешение.
- Блокировка пользователя и отклонение объявления требуют причины.
- Все действия пишутся в audit log.
- Модератор не может управлять платформенными ролями.

### 10.7. Приёмка

- `pytest` зелёный.
- Сценарий: вход → организация → объявление → модерация → поиск → контакты после входа.
- `docker compose up` поднимает API, PostgreSQL и Redis.
- README описывает запуск, seed, админа и вебхук.
