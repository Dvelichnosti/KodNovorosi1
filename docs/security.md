# Безопасность

Документ описывает модель угроз, реализованные механизмы защиты и
обязательные меры для production.

## 1. Модель угроз (кратко)

| Угроза | Защита |
|---|---|
| Подбор пароля | Паролей нет; вход через Telegram deep-link |
| Перехват access-токена | Короткий TTL (15 минут), HTTPS, минимальные claims |
| Кража refresh-токена | Ротация, SHA-256 в БД, обнаружение повторного использования |
| Компрометация админ-аккаунта | Обязательный TOTP, отдельные платформенные права |
| Эскалация прав в организации | Проверка подмножества прав, owner-only операции |
| Спам и флуд | Rate limit на вход, жалобы и загрузки |
| Утечка контактов | Контакты скрыты без авторизации |
| Загрузка вредоносных файлов | Белый список MIME, лимит размера, случайные имена |
| Подделка Telegram-вебхука | Секретный заголовок `X-Telegram-Bot-Api-Secret-Token` |
| Утечка секретов в логи | Секреты не логируются; ошибки возвращают общий текст |

## 2. Аутентификация

### 2.1. Вход через Telegram

- Пользователь не вводит пароль.
- Одноразовый токен входа живёт 10 минут и хранится в БД только как SHA-256.
- После подтверждения сессия помечается `consumed`; повторный poll возвращает
  `410 login_used`.
- Телефон считается подтверждённым, потому что приходит из Telegram.
- `telegram_id` уникален; при совпадении телефона аккаунты связываются.

Рекомендации:

- использовать HTTPS для всех внешних запросов;
- не логировать `token`, `login_url` и содержимое вебхука целиком;
- ограничить доступ к БД и Redis private network.

### 2.2. JWT

Access-токен:

- алгоритм HS256;
- `SECRET_KEY` не короче 32 байт;
- claims: `sub`, `type`, `mfa`, `jti`, `iat`, `exp`;
- TTL 15 минут;
- не содержит персональных данных и прав — права загружаются из БД.

Проверка:

- подпись и срок;
- `type == "access"`;
- пользователь существует и не заблокирован;
- для админ-API — `mfa=true`.

### 2.3. Refresh-токены

- Случайная строка 48 байт (`token_urlsafe`).
- В БД — SHA-256.
- TTL 30 дней.
- При ротации старый токен отзывается, новый получает тот же `family_id`.
- Повторное использование отозванного токена отзывает всё семейство и
  возвращает `refresh_reuse_detected`.
- `logout` отзывает один токен, `logout-all` — все токены пользователя.
- Блокировка пользователя отзывает все refresh-токены и запрещает доступ по
  access-токену на уровне проверки статуса.

### 2.4. TOTP

- Доступен только пользователям с платформенной ролью.
- Секрет генерируется `pyotp` (base32), шифруется Fernet.
- Ключ шифрования — SHA-256 от `SECRET_KEY`.
- Проверка кода — окно ±1 шаг (30 секунд).
- Включение TOTP требует подтверждения кодом.
- Токены после TOTP содержат `mfa=true`.
- Админ-API без `mfa=true` возвращает `403 mfa_required`.

Важно: смена `SECRET_KEY` ломает расшифровку существующих TOTP-секретов.
Планируйте ротацию ключа с перевыпуском TOTP.

## 3. Авторизация

### 3.1. Платформенные права

Проверяются в `require_platform_permission`:

1. пользователь аутентифицирован;
2. в токене `mfa=true`;
3. у пользователя есть роль с нужным кодом права.

Права:

| Код | Возможности |
|---|---|
| `users.view` | Просмотр пользователей |
| `users.block` | Блокировка/разблокировка |
| `orgs.verify` | Верификация организаций и документов |
| `listings.moderate` | Модерация и продвижение объявлений |
| `complaints.handle` | Обработка жалоб |
| `catalog.manage` | Каталог и атрибуты |
| `roles.manage_platform` | Платформенные роли |
| `plans.manage` | Тарифы |
| `audit.view` | Аудит |
| `settings.manage` | Настройки |

### 3.2. Организационные права

- Владелец имеет все права.
- Сотрудник получает права из своей роли.
- Проверка идёт через `require_org_permission`.
- Кэш прав в Redis на 5 минут; при изменении роли/участника кэш
  инвалидируется.
- Нельзя выдать право, которого нет у выдающего.
- Нельзя изменить роль владельца или удалить владельца.
- Передача владения — только владельцем.

### 3.3. Проверка владения объявлением

- Автор объявления может редактировать/удалять/публиковать его.
- Сотрудник организации — только при наличии соответствующего права.
- Просмотр черновиков и отклонённых объявлений — автор или участник
  организации.

## 4. Приватность контактов

- В публичном поиске и карточке без авторизации `contacts=null`,
  `contacts_available=false`.
- С авторизацией контакты возвращаются.
- Публичная карточка организации показывает её контакты, так как это витрина.
- В `listing_views` хранится только SHA-256 от IP, не сырой адрес.

## 5. Загрузка файлов

- Белый список MIME:
  - изображения: `image/jpeg`, `image/png`, `image/webp`;
  - документы: `application/pdf`, `image/jpeg`, `image/png`.
- Максимальный размер — `MAX_UPLOAD_MB` (20 МБ).
- Имя файла генерируется случайно, оригинальное имя хранится только в БД.
- Файлы раскладываются по `kind/<owner_id>/`.
- Публичные типы: `image`, `logo`; документы — приватные.
- Проверка MIME на уровне приложения недостаточна: рекомендуется антивирус
  (ClamAV) и проверка сигнатур в production.

## 6. Rate limiting

Реализовано через Redis `INCR` + `EXPIRE`.

| Ключ | Лимит по умолчанию |
|---|---|
| `login-start:<ip>` | 10 / 60 сек |
| `login-poll:<token>:<ip>` | 60 / 60 сек |
| `complaint:<user>` | 5 / 3600 сек |
| `upload:<user>` | 30 / 3600 сек |

При превышении — `429` и `Retry-After`.

В production обязателен общий Redis. При fallback-кэше лимиты считаются
отдельно в каждом процессе.

## 7. Секреты и конфигурация

Обязательные секреты:

- `SECRET_KEY` — JWT и шифрование TOTP;
- `TELEGRAM_BOT_TOKEN`;
- `TELEGRAM_WEBHOOK_SECRET`;
- пароль PostgreSQL;
- пароль Redis (если включён).

Требования:

- не хранить `.env` в git;
- использовать secret manager (Vault, AWS Secrets Manager, Docker secrets);
- `SECRET_KEY` — минимум 32 случайных байта;
- разные секреты для dev/staging/prod;
- ротация токена бота и webhook secret по регламенту;
- не логировать заголовок `Authorization`, тело `/auth/*`, TOTP-коды.

## 8. CORS и HTTP

- `CORS_ORIGINS` в production — конкретные домены, не `*`.
- `allow_credentials` включается только при явном списке origin.
- HTTPS обязателен; HSTS на reverse proxy.
- Рекомендуемые заголовки на proxy:
  - `Strict-Transport-Security`;
  - `X-Content-Type-Options: nosniff`;
  - `X-Frame-Options: DENY`;
  - `Referrer-Policy: no-referrer`;
  - `Content-Security-Policy` для фронтенда.
- Ограничить размер тела запроса на proxy (кроме `/uploads`).

## 9. Аудит

В `audit_logs` пишутся:

- блокировка/разблокировка пользователя;
- выдача/снятие платформенных ролей;
- верификация организации и документов;
- модерация объявлений;
- обработка жалоб;
- изменения каталога, тарифов, ролей, настроек.

Поля: `actor_id`, `action`, `entity_type`, `entity_id`, `payload`, `ip`,
`created_at`.

Аудит доступен только с правом `audit.view`. Журнал не редактируется через API.

## 10. Обработка ошибок

- Наружу не отдаются stack trace и SQL.
- Непредвиденная ошибка → `500 internal_error`.
- Ошибки валидации → `422 validation_error` с деталями полей.
- Доменные ошибки → `AppError` с кодом и сообщением.
- Логи содержат метод, путь и traceback, но не секреты.

## 11. Чек-лист production

- [ ] `ENV=production`, `DEBUG=false`.
- [ ] `SECRET_KEY` заменён на случайный 32+ байта.
- [ ] `DATABASE_URL` и `REDIS_URL` указывают на защищённые сервисы.
- [ ] `AUTO_CREATE_TABLES=false`, миграции применены.
- [ ] `CORS_ORIGINS` содержит только реальные домены.
- [ ] Настроен HTTPS и HSTS.
- [ ] `TELEGRAM_WEBHOOK_SECRET` задан.
- [ ] TOTP включён у всех администраторов.
- [ ] Включены бэкапы PostgreSQL и проверено восстановление.
- [ ] Настроен мониторинг `/ready`, 5xx и задержек.
- [ ] Ограничен доступ к `/media` (при необходимости).
- [ ] Настроен антивирус для загрузок.
- [ ] Ротация логов и retention.
- [ ] Проверены rate limits под нагрузкой.
- [ ] Проведён review платформенных ролей и прав.

## 12. Реагирование на инциденты

1. **Подозрение на утечку токена**
   - отозвать refresh-токены пользователя (`logout-all` или блокировка);
   - проверить `audit_logs` и `refresh_tokens`;
   - при компрометации `SECRET_KEY` — сменить ключ, перевыпустить TOTP,
     инвалидировать все сессии.
2. **Массовый спам**
   - заблокировать аккаунты;
   - проверить объявления и жалобы;
   - временно снизить лимиты.
3. **DDoS**
   - включить защиту на proxy/CDN;
   - ограничить rate limit на уровне edge;
   - проверить `429` и деградацию Redis.
4. **Утечка файлов**
   - проверить права на `/media`;
   - переместить приватные документы в object storage с private ACL;
   - уведомить ответственных по регламенту.
5. **Компрометация БД**
   - изолировать сервис;
   - восстановить из проверенного бэкапа;
   - сменить все пароли и секреты;
   - проанализировать `audit_logs`.

## 13. Ограничения MVP

- Нет 2FA для обычных пользователей (только для платформенных ролей).
- Нет автоматической проверки ИНН через ФНС.
- Нет антивирусной проверки загрузок.
- Нет WAF и защиты от ботов на уровне приложения.
- Нет шифрования данных в БД на уровне полей (кроме TOTP-секретов).
- Нет детального журнала чтения (только изменения).
